# Task_0001 知识点总结

## 1. 先把自然语言要求转换成明确规则

交易员提出：

> 若今日收盘价大于今日开盘价，则于次日开盘价买进 1 手。

开发时需要拆成四个明确部分：

1. **判断时间**：今天的日 K 收盘后。
2. **判断条件**：`今日收盘价 > 今日开盘价`，等于时不买。
3. **成交时间**：下一交易日开盘。
4. **交易动作**：期货买入开仓 1 手。

还要确认连续多天满足条件时是否每天加仓。本任务当前约定为每天增加 1 手，没有持仓上限。

## 2. 信号时间不等于成交时间

当天收盘后才能知道当天是否为阳线，因此不能使用当天开盘价成交。

正确时间顺序是：

```text
今日开盘 → 今日收盘 → 产生信号 → 次日开盘买入
```

代码在当前日 K 结束后调用 `buy_open`，但必须确认所用 QMT/iQuant 回测撮合模型确实把订单放到下一根日 K 开盘成交。

## 3. 持仓损益与平仓不是一回事

### 统计持仓损益

- 仓位仍然存在。
- 使用当前或回测结束时的价格计算浮动盈亏。
- 没有发送平仓订单。

### 平仓

- 发送与原持仓方向相反的平仓订单。
- 成交后仓位减少或归零。
- 盈亏由浮动盈亏变成已实现盈亏。

本任务在 2026-07-16 回测结束时，使用最后一根日 K 收盘价 4377 统计仍持有仓位的损益，不执行平仓。

## 4. 面板参数与代码参数要分开

### 由面板控制

- 默认品种，例如 `jd2609`。
- 回测开始和结束日期。
- 复权方式，本任务选择“不复权”。
- 初始资金、手续费、滑点和其他回测参数。

### 由代码控制

- 使用日 K 的开盘价和收盘价。
- 阳线条件：`close > open`。
- 每次买入开仓 1 手。
- 不允许在运行或实盘模式下单。
- 不设置平仓条件。

原则：需要经常在不同回测中更换的设置尽量放面板；决定策略含义的规则保留在代码中。

## 5. 读取默认品种不能误用股票池

`ContextInfo.get_universe()` 读取当前股票池或品种池，但右侧“默认品种”不一定自动进入该列表。因此，即使面板显示 `jd2609`，也可能得到空列表。

当前图品种应通过以下属性读取：

```python
contract = ContextInfo.stockcode + '.' + ContextInfo.market
```

也可以先分别从面板读取股票/合约代码和市场，再拼成完整代码：

```python
stock_code = ContextInfo.stockcode
stock_market = ContextInfo.market
contract = stock_code + '.' + stock_market
```

- `ContextInfo.stockcode`：面板当前默认品种的代码部分。
- `ContextInfo.market`：该品种所属市场的后缀。
- 如果接口只需要代码或市场，可以直接使用前两个变量；需要完整证券代码时再组合为 `代码.市场`。

界面与代码位置可参考[iQuant 面板默认品种与代码提取示例](参考/iQuant面板默认品种与代码提取示例.png)。截图用于确认字段和面板位置，不代表其中显示的整段策略已经完成验收。

例如：

```text
stockcode = jd2609
market    = DF
contract  = jd2609.DF
```

然后把该合约加入行情池：

```python
ContextInfo.set_universe([contract])
```

虽然接口名称中使用 `stockcode` 和“股票池”，这些名称也用于期货等其他交易品种。

官方参考：[ContextInfo 变量与函数检索](https://dict.thinktrader.net/VBA/check_sheet.html)

## 6. 回测开始日期会影响第一笔交易

面板从 2026-07-01 开始回测，没有包含 2026-06-30，因此代码不能利用 6 月 30 日的收盘条件。

所以：

- 7 月 1 日开盘不会因为 6 月 30 日的行情买入。
- 代码从 7 月 1 日日 K 开始判断。
- 如果 7 月 1 日为阳线，最早在下一交易日开盘买入。

这体现了一个重要原则：回测只能使用回测起点以后已经获得的信息。

## 7. 回测结束日期也会影响最后一个信号

如果结束日当天是阳线，代码可能产生买入信号，但回测范围内没有下一根日 K，因此这笔订单不应成交。

需要在回测结果中确认：

- 结束日信号没有被错误地按当天收盘成交。
- 没有产生超出回测范围的持仓。
- 未成交委托是否会出现在报告或日志中。

## 8. 期货通常不需要股票复权

股票会因分红、拆股等公司行为产生复权需求。期货合约不是股票，本任务使用具体合约 `JD2609`，面板选择“不复权”。

如果以后改用主力连续或自建连续合约，还需要另外确认换月和价格拼接规则；那不是股票复权，但同样会影响历史价格序列。

## 9. 合约乘数什么时候需要

如果让 QMT/iQuant 回测系统计算账户和持仓损益，策略代码不需要手工写合约乘数。

只有代码自己计算金额盈亏时，才需要类似：

```python
pnl = (current_price - entry_price) * contract_multiplier * lots
```

手工计算还必须考虑方向、手续费、滑点和实际成交价，因此本任务 v2 删除了手工盈亏计算。

## 10. 优秀开发人员应主动确认的问题

拿到类似策略时，应在写代码前主动询问：

1. `收盘价 > 开盘价` 是严格大于，还是大于等于？
2. 连续满足条件是否连续加仓？
3. 最大持仓手数是多少？
4. 已经持仓时是否还能继续买入？
5. “次日开盘价买进”使用哪种回测撮合设置？
6. 最后一天产生的信号如何处理？
7. 回测结束时是保持持仓、统计损益，还是实际平仓？
8. 结束估值使用收盘价还是结算价？
9. 手续费、滑点、保证金和初始资金如何设置？
10. 商品、日期、周期和复权方式由面板控制还是代码控制？
11. 代码只用于回测，还是以后需要运行或实盘？
12. 验收结果依据哪一份行情数据和哪个软件版本？

先确认这些问题，可以避免代码虽然能运行，却实现了错误的交易意图。

## 11. 版本保存方法

同一个任务的不同要求不能互相覆盖：

```text
Task_0001/
├── v1.py
├── v1说明.md
├── v2.py
├── v2说明.md
└── 知识点总结.md
```

- `v1` 保存最初的硬编码实现。
- `v2` 保存面板控制品种、日期和复权方式的实现。
- 每版说明必须记录老板要求、面板设置、代码行为、验收结果和与上一版的差异。

## 12. 扩展学习：Python 量化工具

TASK_0001 当前使用 QMT/iQuant 自带接口运行，下面三个 Python 库不是本策略的依赖。它们适合以后在独立 Python 环境中进行金融建模、策略回测和跨平台验证。

### QuantLib

- 面向金融建模、交易与风险管理的开源库，核心使用 C++ 编写，并提供 Python 等语言接口。
- 适合衍生品定价、收益率曲线、利率模型和风险分析等工作。
- 它的主要定位是金融工具与定价模型库，不是专门的通用策略回测引擎。

官方资料：[QuantLib](https://www.quantlib.org/)

### Backtrader

- Python 策略开发与回测框架。
- 通常通过数据源、`Strategy` 和 `Cerebro` 引擎组织回测，并可加入观察器、分析器和绘图。
- 可用于把 TASK_0001 的阳线买入规则移植到独立环境，用同一份历史数据复核信号、成交和绩效。

官方资料：[Backtrader 文档](https://www.backtrader.com/docu/)

### Zipline

- Quantopian 开源的 Python 事件驱动型算法交易与回测库，可与 Pandas 等 Python 数据分析工具配合。
- Quantopian 原始仓库的最新公开版本较旧，安装说明对应的 Python 版本也较旧，不宜直接视为当前环境的安装指南。
- 新项目如果考虑 Zipline，应同时评估仍在维护的社区分支 `zipline-reloaded`，并核对操作系统、Python 版本、数据接入和交易日历兼容性。

参考资料：[Quantopian Zipline 原始仓库](https://github.com/quantopian/zipline)、[Zipline Reloaded](https://github.com/stefan-jansen/zipline-reloaded)

### 与 TASK_0001 的关系

- 在其他框架复现时，必须保持相同规则：当日收盘确认阳线，下一交易日开盘成交，每次 1 手，回测期间不主动平仓。
- 不同框架的撮合时点、手续费、滑点、合约乘数和期货交易日历可能不同；结果不一致时，应先检查这些设置，而不是直接判断策略代码错误。
- 第三方 Python 库应安装在独立研究环境中。未经兼容性验证，不要直接导入 QMT/iQuant 内置 Python 环境。
