# 代码组织与说明指南

## 代码分别放在哪里

| 内容 | 目录 | 说明 |
|---|---|---|
| 可复用 Python 逻辑 | `src/quant_trading/` | 正式代码，有清晰接口并接受自动化测试 |
| 一次性运行入口 | `scripts/` | 下载数据、批量回测、生成报告等薄脚本 |
| 探索性实验 | `notebooks/` | 可视化和快速验证；成熟逻辑应迁出 |
| 自动化测试 | `tests/` | 文件名与 `src/` 模块对应，例如 `test_metrics.py` |
| 最小调用示例 | `examples/` | 展示接口如何使用，不承载核心逻辑 |
| 策略说明文档 | `strategies/` | 经济逻辑、规则、假设和失效条件 |
| 研究过程记录 | `research/` | 数据版本、参数、实验结果和研究结论 |

`strategies/` 与 `src/quant_trading/strategies/` 的职责不同：前者回答“为什么研究、规则是什么”，后者才是可运行的策略实现。

## 推荐模块边界

随着项目增长，可在 `src/quant_trading/` 下逐步增加：

```text
quant_trading/
├── data/        # 数据读取、清洗、校验和交易日历
├── features/    # 指标、因子和特征工程
├── strategies/  # 只根据输入生成信号或目标仓位
├── backtest/    # 组合推进、交易成本与成交模拟
├── portfolio/   # 仓位、再平衡和组合构建
├── risk/        # 风险约束、压力测试和停机条件
├── execution/   # 订单转换与经纪商适配
├── reporting/   # 绩效统计、图表和研究报告
└── metrics.py   # 当前提供的基础绩效指标示例
```

先按学习需要创建模块，不要一次性生成空架构。

## 每个代码文件的描述要求

每个模块顶部写模块级 docstring，说明用途、输入假设和不负责的范围。每个公开函数至少说明：

- 参数的类型、单位和时间频率；
- 返回值及其方向，例如最大回撤返回非正数；
- 缺失值、空输入和非法值如何处理；
- 公式或约定与常见实现有何差异；
- 对应研究记录、论文或策略卡片的位置。

`src/quant_trading/metrics.py` 是最小示例。

## 从研究到正式代码

1. 在 `research/` 写可证伪假设和数据说明。
2. 在 `notebooks/` 做最小实验，保留失败结果。
3. 把稳定逻辑迁入 `src/quant_trading/`，减少全局状态和隐藏参数。
4. 在 `tests/` 增加正常输入、边界值和错误输入测试。
5. 在 `examples/` 给出最小调用方法。
6. 回到研究记录，链接代码版本并写下结论。

## 编码约定

- 使用 Python 3.11 或更高版本，并为公开接口添加类型标注。
- 金额、收益率和年化方式必须写明单位与约定。
- 时间序列切分必须保持时间顺序，禁止随机打乱后评价交易策略。
- 数据获取、信号生成、仓位计算和执行适配应分层，避免相互隐藏依赖。
- 密钥只通过环境变量或密钥管理服务读取，禁止提交到 Git。
- 新增第三方依赖时同时更新 `pyproject.toml` 并说明用途。
